# v0.1.0-alpha.9

プロファイルのリースを取れなかったDSHが、相手の心拍が止んだあと取り直して自動接続できるようにします。開発プレビューを継続します。

## 変更内容

- 起動時に`owner.lock`を取れない場合でも、DSHのWeb起動は待ちません。プラグインは読み込んだまま設定画面で`LOCK`を表示し、観測と取り直しはバックグラウンドで行います。最初の取り直しは直ちに観測し、その後は心拍の約2倍から倍々、上限1分の間隔で`Store.open()`をやり直します。更新が続いているロックは取りません。成功すると通常のコントローラーへ切り替わり、自動接続が有効なら再開します。取り直しのタイマーはプラグインの破棄で止まり、失敗した`Store`は閉じます。同時の取り直しでも持ち主は1つです。
- `owner.lock`には、起動したcloudflaredのPIDと開始時刻を記録します。Linuxは`/proc/<pid>/stat`のstarttime、macOSは`ps -o lstart= -p <pid>`、WindowsはプロセスのStartTimeです。この記録はリースの判定には使いません。新しい持ち主は、cmdlineに`cloudflared`が含まれ開始時刻が一致するプロセスだけをSIGTERMし、約5秒で終わらなければSIGKILLします。そのプロセスが居なくなったことを確認してから、自分のcloudflaredを起動します。PIDが再利用されたプロセスは止めません。開始時刻を読めない、記録に開始時刻が無い、またはSIGKILLの約2秒後もプロセスが残っているときは、そのプロセスを止めず、新しいcloudflaredも起動せず、理由付きの`LOCK`を表示します。
- 再開では保存済みゲートポートを動かさず、cloudflaredより先にそのポートをbindします。bindできないときはcloudflaredを起動せず、`GATE_PORT_BUSY`を約1秒ごとに再試行します。
- プロセスが一時停止して心拍だけが止まった場合に、後のDSHがリースを取るのはこの仕組みの動作です。動いている古いDSHは`assertOwnership`で喪失に気づき、stateとtokenを書かずに自分のcloudflaredを止めます。これは二次的なガードです。SIGSTOP中のプロセスは自分では確認できません。
- ロックの案内を、英語・日本語・中国語とも「このDSHを再起動する」に変更しました。
- 設定画面のボタンは狭い幅で折り返し、カードの外へ出ません。DSHの設定ダイアログがプラグインに渡す幅は約106pxで、本文が1〜2文字で折れるのはその幅のためです。
- 画面上に更新ボタンはありません。入れ替えは次のコマンドです。

## 導入・更新

```sh
dsh plugin --profile web add -w 'github:Aero123421/dsh-cf#v0.1.0-alpha.9'
```

DSHを再起動し、ブラウザを再読み込みしてください。既存の公開設定とconnector tokenは保持します。管理用APIトークンは保存しないため、設定変更時に再入力します。

## リリースへ tarball と SHA256SUMS を付ける

このリポジトリはソースから導入します。GitHub Releaseへ配布物を付ける場合は、Releaseの作成と公開は手元で行い、ファイルだけを用意します。

手動:

```sh
npm ci
npm pack --pack-destination dist
( cd dist && sha256sum dsh-cf-*.tgz > SHA256SUMS )
```

`dist/dsh-cf-0.1.0-alpha.9.tgz` と `dist/SHA256SUMS` を、作成する Release の資産としてアップロードします。`SHA256SUMS` の行は `sha256sum -c` で照合できます。

同じ成果物を Actions の artifact として作るワークフローが `.github/workflows/release-assets.yml` です。`workflow_dispatch` だけで動き、GitHub Release は作りません。artifact をダウンロードして、手元の Release へ添付します。

## 検証

Linux、Node.js 22.23.3。`npm run check` は成功。`npm run check:dsh` は、公開されている `evaluatePluginCompatibility` が peer `>=0.2.1-alpha.2 <0.3.0-0` を `0.2.1-alpha.2`、`0.2.1-alpha.3`、`0.2.1-alpha.5`、`0.2.1-rc.2` で受け付け、`0.2.1-alpha.1` と `0.3.0-0` を拒否することを確認した。

同じマシンの DSH `0.2.1-rc.2`、ローカルの TLS エッジ、テスト用 cloudflared で起動時間を測った。ロックがないときの Web の待受は約 1.9–2.1 秒、公開がオンラインになるのはその約 0.4 秒後。`0.1.0-alpha.8` では `kill -9` のあと Web の URL が出るまで 10.2 秒、動いている相手がいるときの 2 台目は 10.0 秒だった。この版では同じ操作で Web の URL は 1.8 秒と 2.1 秒で、設定画面は直ちに `LOCK` になる。相手を `kill -9` したあと、待っていた側は 8.3 秒でオンラインになり、その間の cloudflared は最大 1 プロセスだった。単独の `kill -9` からオンラインまでは 10.2 秒で、うち Web の待受は 1.9 秒。動いている cloudflared を `kill -9` すると 5.3 秒でオンラインに戻った。その後の待ちは 5・15・30・60・120 秒、以後 300 秒である。連続してすぐ終了する代役では、状態表示は `reconnecting` のままなので、15 秒以降の間隔は画面の切り替わりとしては分けて記録していない。

設定画面のボタンは、幅 390px のときプラグイン欄 106px の内側に収まった。幅 320px ではボタンの右端が欄を最大 3px 超える。これは P3 で、DSH 本体の設定ダイアログがビューポートより広くなる既知の問題である。プラグイン側でこの 3px を解消する変更は入れていない。

実Cloudflare・実cloudflared接続、実IdP、Electron、Safari/iPadOSは未検証です。Cloudflare APIと外部エッジはfixture、cloudflaredはテスト用の代役です。macOS の `ps -o lstart=` と Windows の StartTime は、この環境では実行していません。実機で開始時刻の記録と照合を見ていないことは、残るリスクです。
