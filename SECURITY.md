# Security model

This is an unaudited alpha plugin for a **single trusted DSH operator**. DSH can execute programs and access the host's files. Granting access is effectively granting operator control, not a read-only chat account.

## Trust boundaries

The browser trusts Cloudflare TLS, Access, its configured identity provider and MFA policy. Cloudflare terminates public TLS and can inspect or modify web traffic: **this is not end-to-end encryption against Cloudflare**. The local proxy verifies an RS256 app JWT against a pinned team issuer/JWKS URL, exact application audience, required claims, expiration, and one owner email. It never trusts an email header by itself.

Cloudflare's API account and zone are explicitly selected. Provisioning refuses preexisting DNS records, overlapping Access apps, unexpected policy changes, and unknown POST outcomes. A separate per-instance tunnel is used, not a replica of an unrelated machine. Configuration contains no paid-service activation calls.

The proxy preserves public Host and same-origin browser checks. DSH's own launch-token exchange runs only over its loopback listener. Its signed cookie is kept in server memory and stripped from public response headers. The DSH signing secret is never accessed. DSH private implementation objects are not patched.

## Authentication modes

Authorized save updates the owned application session to 168 hours and checks the API readback. A per-policy session override that differs from that value is rejected rather than overwritten. Previously issued tokens retain their old expiration; the new lifetime applies to newly issued sessions. Organization-wide global-session settings are not changed.

New UI setups default to Access sign-in with an owner-email allow policy, one selected IdP, and a one-week (168-hour) application session held in the browser's Access cookie. In this Access-only mode the plugin creates the application **without** `mfa_config`, so it adds no per-application independent MFA of its own; when an existing WebAuthn application is switched to Access-only it sends `mfa_config: { mfa_disabled: true }`. Read-back accepts an absent or null `mfa_config` or `mfa_disabled: true` and rejects anything else (for example `mfa_disabled: false` or an empty object). An organization-wide MFA requirement for all applications is a separate Cloudflare setting that this plugin neither reads in Access-only mode nor overrides; the plugin does not weaken it, and the mode means "no extra factor added by this plugin". **How Cloudflare reports and enforces an application created without `mfa_config`, or switched with `mfa_disabled: true`, together with that organization setting has not been confirmed on a live account**; the behavior above comes from the API schema and local fixtures. The JWT gate, owner-email check, issuer/audience/expiry verification and private management boundary remain required. A stolen valid Access session can grant operator access until it expires or is revoked.

The operator can opt into additional WebAuthn. Saved setups without `requireWebAuthn` retain the original WebAuthn requirement; only explicit boolean `false` selects Access-only mode. Invalid saved or submitted mode values are rejected. Organization authenticator and AMR checks apply only to WebAuthn mode, and enrollment links are hidden for Access-only mode.

Changing modes on an existing publication requires a local authenticated management request, a fresh Cloudflare authorization, and validation of the existing app's marker, hostname, audience, IdP and exact owner policy before writing. The app's MFA configuration and its one-week session duration are updated; an existing per-policy MFA override prevents the change. These updates are idempotent PUTs and record no checkpoint. After a failed PUT the application is read again: equal to the requested values counts as applied, equal to the previous values is an ordinary error, and anything else stops with `ACCESS_CHANGED`. A read-back that does not match is an ordinary error. Checkpoints that older versions left for these two kinds (`session`, `authentication`) no longer block a resume; the next authorized save re-validates the application and clears them. A session-duration-only update keeps earlier verification and auto-connect; only a mode change clears them, and disables automatic reconnection until the real traffic checks pass again. This operation does not change shared organization MFA, recreate the Tunnel/DNS, or adopt unrelated resources.

The public hostname must be exactly one label under the selected zone (`dsh.example.com` for `example.com`). Deeper names are rejected before any write because Cloudflare's free Universal SSL certificate covers one level only.

## Administrative and runtime credentials

There is no OAuth flow: no public OAuth client exists for this plugin, and client secrets and persistent refresh grants are not used. Cloudflare management uses an API token the operator enters on a local management connection. It is held in memory only, expires one hour after it was verified (the expiry time is reported in the status), is discarded when it expires, when the operator forgets it, and when the plugin stops, and a newer token supersedes an older verification still in flight. Late results of a cancelled or superseded request cannot install or restore a grant.

The dedicated Tunnel token is stored as a restricted file; it is **not encrypted with an OS keychain**. No secrets are returned by the status API, put in public DSH URLs, printed by logging code, or passed as command-line argument values. The child connector receives an allowlisted environment rather than model/API credentials.

Original authenticated DSH callers can manage the plugin. The public gate permits only the sanitized `/dsh-cf/status` endpoint from its management channel; all mutations in that channel are blocked, including encoded aliases. This is not a separate privilege boundary against DSH's own operator capabilities: an authenticated DSH operator can run commands and change files. Do not assume the plugin protects the Cloudflare token from other plugins or malicious code executed by that same OS user.

## Streams, cookies, and revocation

Every request that reaches the gate carries an Access JWT that is verified before anything is forwarded, so the DSH session exchange is lazy: the first verified request (an API call, a WebSocket upgrade or a page load, in any order) performs DSH's normal cookie exchange over loopback. There is no separate enable step, verification link or proof nonce. "Owner" evidence is recorded only after both the JWT check and the exchange succeeded. A failed exchange is reported as a DSH problem (HTTP 502/503), not as a sign-in failure, and enables nothing.

If the key endpoint of the Access team cannot be reached (timeout or network failure), the gate answers 503 with a short page saying that this PC could not verify the sign-in and to retry shortly; it does not show the sign-out page. The last successfully fetched key set is kept and used while a refresh fails, for at most 24 hours after the last successful lookup and never for a key id that was not in it. A token that fails verification for any other reason is still refused (401), and a verified account other than the owner gets a page saying the account is not allowed with the Access logout link.

Every new HTTP/WS request is checked. State-changing HTTP and WS requests require the exact browser Origin. Cross-site GET navigation is allowed only at safe entry/verification documents. Incoming cookies/Authorization/forwarded metadata are not used as DSH credentials. The upstream signed cookie is injected after JWT validation.

Uploads are bounded to 100 MiB, header bytes are bounded, up to 256 HTTP requests and, separately, 64 WebSockets are in flight at once, and streams are forwarded with backpressure. WS/SSE/HTTP streams close on the earlier of JWT expiration or 15 minutes. The plugin does not replay writes after an upstream failure. Stopping closes the connector first and then the gate and its sockets, so cloudflared never forwards traffic to a closed port that another program could bind. A guardian notices parent IPC loss and terminates its own child after a DSH crash.

A locally valid JWT does **not** prove the current Cloudflare policy has not just changed. Independent MFA is enforced by Cloudflare; the gate does not receive a cryptographic WebAuthn attestation from the browser. API settings are checked during provisioning, not continuously on every request or offline resume. Edge logout/revocation may not instantly end an established stream. For immediate local revocation, stop this plugin; then revoke Cloudflare sessions/tokens and rotate credentials as needed. An existing local DSH session has separate lifetime and ownership.

## Supply chain and files

The bundled source executes no install/prepare hook. The only application dependency is the pinned `jose` package (v6.2.12). `semver` (v7.8.5) is a development dependency used by the compatibility scripts that mirror app-boot's peer-range check. The lock points at their immutable official release tarballs and published SHA-256. Audit the dependencies and verify `npm ci && npm run check` in a connected environment before release.

cloudflared private downloads use a pinned release version and official release digest, checked before extraction/execution. This trusts Cloudflare's GitHub release account/API and GitHub TLS. It is not independent signature verification. Its executable cache is checked before reuse. Explicit user-selected or previously installed binaries remain the user's trust decision. Existing services, configuration files and other tunnels are not reconfigured.

State/token files are scoped to the active profile, written atomically with POSIX mode 0600 under a 0700 directory. Windows ACLs require environment review. Root/admin access, filesystem snapshots, backups, the same OS user, malicious extensions, and a compromised DSH/runtime can expose these files or process memory. Keep state and token files out of git and shared folders.

## Profile ownership and copied state

`owner.lock` keeps two DSH processes from running one profile's connector. It is a lease: the owner refreshes its mtime every few seconds. PID presence, equality, or absence proves nothing across PID namespaces such as two containers sharing a volume. Every existing lock is observed for longer than one heartbeat interval and reclaimed only if its heartbeat has stopped; a heartbeating lock is refused. Renewal checks the nonce on the opened lock file, so it never refreshes a replacement owner's inode. Ownership is declared lost only when the lock is readable and carries another nonce, when it is gone, or after several consecutive refresh failures; a single transient I/O error is not a loss, and a state write that cannot read the lock is refused without declaring the loss. Detected ownership loss stops this instance's gate and connector and blocks further state/token writes, without recording a pause. A `reclaim.lock` directory left behind by a crash during recovery is treated as stale after about two minutes and removed. If the state cannot be opened (`LOCK`, `STATE_CORRUPT`), plugin activation still succeeds: the settings channel reports status `error` with an actionable issue, writes no state, and refuses every action. The heartbeat assumes a filesystem that updates mtimes, which shared network filesystems may not do reliably, and does not provide atomic distributed transactions.

State records a host identity. Version 2 is derived from the operating system's machine id where it can be read cheaply (Linux `/etc/machine-id` or `/var/lib/dbus/machine-id`, macOS `IOPlatformUUID` through `ioreg`, Windows `MachineGuid` through `reg query`), so renaming the host does not look like a new host. A state that holds only the earlier hostname-based value is upgraded silently on the machine it matches, and that value remains the fallback when no machine id can be read. When the identity differs, the plugin still loads but refuses to connect (boot, start, resume, automatic retry) until the local operator confirms that no other DSH uses the same Tunnel; the auto-connect preference is kept, and after the confirmation an eligible profile resumes by itself. Confirmed identities are remembered. A cloned virtual machine image keeps its machine id, so this safeguard cannot tell such a clone from the original. It guards against accidentally running a copied profile twice; it is not cryptographic device binding.

## Unknown writes

The POST that creates the Access application, Tunnel or DNS record can succeed on Cloudflare while its response is lost. The plugin then keeps a checkpoint, blocks reconnecting and never repeats the POST on its own. `pending/inspect` lists, with GET requests only, the resources that exactly match this instance's marker `dsh-cf-<instance id>` (and the hostname for Access and DNS); the saved path is never used as a request target. `pending/resolve` lets the local operator finish the recovery. It needs a management connection, a current API token, the exact hostname, and it inspects Cloudflare again itself instead of trusting anything the client sends:

- `clear-recorded` clears the checkpoint only if every exact match is the ID this instance already recorded.
- `delete-unrecorded` deletes only exact matches that are not the recorded ID, after reading each one again and re-checking its marker (Access: name and domain; Tunnel: name, not deleted, connections removed first; DNS: name, comment, CNAME), then clears the checkpoint. It never deletes the recorded ID and adopts nothing.
- `clear-not-found` clears the checkpoint only when the inspection finds no match. **Residual risk:** a write that Cloudflare completes after the inspection would leave a resource this plugin never records; the operator's confirmation is the safeguard, and the next inspection or a manual look at the Cloudflare dashboard finds it.

Automatic idempotent updates (session duration, authentication mode) do not create checkpoints.

## Settings channel

The `/dsh-cf/<action>` channel is registered on DSH's WebServer route table and admits each request with DSH Connection's own Host/Origin/cookie fence (`connection.requestRejection()`), using the same JSON envelope as DSH RPC. `connection.rpc.handle()` is not used because in DSH 0.2.1-alpha.2 it throws for plugin contexts. Over the public hostname the gate additionally allows only the read-only `status` action.

Every settings action except the read-only `status` requires `isManagementRequest` before the body is handled, and the controller refuses actions that do not carry that decision. That includes authorize, account, MFA enable, start, resume, pause, cancel, token refresh, host confirmation, auto-connect, forget, remove, `pending/inspect` and `pending/resolve`. `status` stays available after DSH's own admission check, and the decision is made per request: a management request receives the full status (`canManage: true`), while any other caller, including the public tunnel, receives only the status word, a safe issue text, the public URL, verification time and the auto-connect and pause flags (`canManage: false`), with no account lists, resource IDs, local paths, ports, setup or team domain. The decision is the TCP peer address: it must be loopback, the Host must also be loopback, and forwarding headers (`forwarded`, `x-forwarded-for`, `x-forwarded-host`, `x-real-ip`, `cf-connecting-ip`, `true-client-ip`) must be absent. A public peer that sends `Host: 127.0.0.1` is denied. A loopback peer with a public Host is denied too. Host never grants management by itself. An undefined peer fails closed. The public gate's browser fence requires the configured public hostname and still allows only POST `/dsh-cf/status`; a Host of `127.0.0.1` or `localhost` is rejected there and is not treated as an operator. Outbound DSH cookie exchange connects to the loopback address reported by DSH's WebServer and sets Host to the public hostname; it does not choose that address from an inbound Host header. Status snapshots omit the authorization code, the management token, and the tunnel token.

Recovery from a failure uses only the saved connector token. At DSH start (auto-connect on, not paused, host confirmed, configuration previously checked, no unknown write) and when the connector exits while the publication is up, the plugin retries after 5, 15, 30, 60 and 120 seconds and then every 300 seconds. It retries cloudflared start/registration failures and exits, a failed external unauthenticated-rejection probe, DSH listener/API/connection failures and a busy saved gate port. It does not retry an unauthenticated success at the edge (`UNPROTECTED`, which stays stopped), incomplete setup, host review, unknown writes, lock or state errors, executable problems, or resource mismatches. Retry timers are unreferenced, owned by the controller, and cancelled by pause, start, resume, remove, cancel and dispose; each timer compares a generation so a stale one cannot revive a paused or removed publication. A pause is stored in the state (`paused`) and is honored at boot; the auto-connect preference is separate and unchanged. Shutdown by dispose or ownership loss does not store a pause. Cancel aborts only the operation and management requests in flight: it never stops a healthy publication when only a side request is cancelled, and an operation that was already rebuilding the runtime closes its partial runtime.

If the saved gate port is busy, a resume fails as `GATE_PORT_BUSY` (retryable) because the Tunnel routes to that port and no Cloudflare write is allowed. An authorized start binds a new port and updates the owned Tunnel's ingress: the owned Tunnel is verified by its marker, the current ingress is compared with the desired one, and a PUT is sent only for a first-time configuration or a change of the local port alone, followed by an exact read-back. Any other difference is refused as `TUNNEL_CHANGED`.

When the plugin adds the public hostname to DSH's `trustedHosts` through the official configEditor it records exactly that edit (array entry or the expression wrapper it created). Deleting the public configuration reverts only that edit: the single array entry (removing the key again if the plugin created it) or the exact wrapper. If configEditor refuses the edit or the form was changed, the entry is left and its name is reported as `trustedHostLeft`.

In WebAuthn mode, organization MFA is read from `allowed_authenticators` together with `amr_matching_enabled`, `amr_matching_session_duration`, and `amr_session_duration`. Any enabled flag or valid duration blocks publication as a substitute. A malformed value blocks publication as unknown. For a recognizable MFA configuration (an authenticator array and valid session duration), omitted/null AMR fields mean the optional AMR matching setting is unset, matching the organization API schema. Missing or malformed MFA configurations remain indeterminate and block publication. A duration of `0m` is configured AMR matching and is not treated as disabled. An explicit `amr_matching_enabled: false` with neither duration is independent WebAuthn. This plugin does not turn the shared IdP-MFA shortcut off. A tunnel-token refresh reads the owned tunnel by its stored ID and marker, then replaces the local file only when the API value is the original base64 JSON connector token (`a` account id, `t` tunnel id, `s` secret of at least 32 bytes) and those ids match this instance. The token returned when the Tunnel is created is stored only after the same check. A failed or cancelled refresh does not replace the file. A failed refetch leaves a running gate and connector in place. If the new token cannot restart a running connector or resume a finished setup, the refresh does not report success. It does not create another Tunnel, DNS record, or Access app. Offline resume keeps using the saved token and does not require a management grant. A HTTP 5xx or 401 from DSH is forwarded as is (a WebSocket upgrade that receives one follows the same rule); it keeps the status `online` and sets a warning that the next successful request clears, and it never removes observed evidence or the saved verification time. A 5xx before any success on that channel is not recorded as success, and a closed tab or an ended WebSocket is not a fault. The status word `online` means that the gate listens and the connector is connected, and it does not depend on a browser being connected. These MFA, token, and upstream paths were checked with local API fixtures, not a live Cloudflare account or IdP.

## Live validation status

Plugin version `0.1.0-alpha.2` was validated on real DSH `0.2.1-alpha.2` (npm, Linux, web profile), with Cloudflare's edge emulated by a local TLS proxy and Access JWTs signed by a local RSA key: plugin install and load, settings UI and channel admission, `trustedHosts` persistence through configEditor and the resulting Connection reload, launch-token cookie exchange, HTTP/API/WebSocket proxying, rejection of missing/wrong-owner/expired JWTs and of public management, launch tokens and cross-origin requests, automatic UI reconnection after forced stream closure, boot-time auto-connect launching the real cloudflared 2026.10.0 with its exact flags, connector and guardian cleanup after `kill -9` of DSH, stale-lock recovery, and the host-identity review. The real JOSE RSA/JWT tests run in `npm run check`.

Version `0.1.0-alpha.3` adds local regression coverage for overlapping shutdown, authorization replacement, management-operation cancellation, rejected WebSocket cleanup, per-connection Tunnel status, and configuration readback. These local fixtures do not establish live Cloudflare compatibility; the release remains a developer preview.

`@deepseek-ai/dsh` is declared as `>=0.2.1-alpha.2 <0.3.0-0`. DSH `0.2.1-alpha.2` and `0.2.1-alpha.3` both accept a peer when `semver.satisfies(runtime, range, { includePrerelease: true })` is true, so this range is intended to load on those versions and on later `0.2.x` prereleases. On Linux with Node.js 22.23.3, both the reviewed commit's tarball and the tarball that includes these fixes were installed into fresh web profiles of the published npm packages `@deepseek-ai/dsh@0.2.1-alpha.2` and `@deepseek-ai/dsh@0.2.1-alpha.3`. In all four cases `dsh web` listened: unauthenticated `GET /` returned 401, the launch-token exchange returned 303 and a cookie, `GET /` with that cookie returned HTML 200, and `POST /dsh-cf/status` returned a server response with `ok: true`, phase `idle`, and version `0.1.0-alpha.4`. The response body did not contain the launch token. That check does not repeat the alpha.2 proxy, JWT, `trustedHosts`, or cloudflared checks, and it does not use a live Cloudflare account. The published `dsh` CLI runs only when `import.meta.main` is true. That property arrived in Node.js 22.18.0. On Node.js 22.14.0 it is undefined, and `dsh --version` for both `0.2.1-alpha.2` and `0.2.1-alpha.3` exited 0 with empty stdout and stderr, so no listener started. Node.js 20.x does not provide `import.meta.main`, so the same CLI exits without output. This package declares `engines.node` as `>=22.18.0`. Node.js 22.23.3 set `import.meta.main`, and the listeners above started.

In particular confirm how a live account reports an application created without `mfa_config` and one switched with `mfa_disabled: true`.
- With a real Access application: normal owner login with WebAuthn, incorrect user, expiry, key rotation (including the 24-hour key fallback), logout, revoked sessions, and Tunnel registration through the edge.
- Automatic recovery against a real cloudflared connection loss and a real Tunnel ingress update after a port change.

Do not add bypasses to work around a failed integration test. Leave publication stopped, report the failing boundary, and fix the integration.

## Reporting

Do not publish live tokens, callback URLs, cookies, private files, or exploitable proof against deployed installations in a public issue. Prefer GitHub private vulnerability reporting if enabled; otherwise ask the maintainer for a private reporting channel without including exploit details. No formal audit or response SLA is claimed.

## Status generation and replacing a working publication

Status carries a random, process-local controller generation as well as its sequence. Client reconciliation retires prior generations, drops their delayed replies, and clears transient authorization inputs when a new Host generation appears. These identifiers grant no authority.

Before replacing a working publication, input validation, identity consistency, DSH readiness and binary checks complete first. A refusal in that phase leaves the running connection and prior configuration checkpoint intact; errors after replacement begins still stop the new publication. A read that fails transiently while saving settings leaves the earlier configuration check in place; the check is voided right before a Cloudflare write and when a read-back shows a mismatch. Multiple authenticated WebSockets are counted independently.
